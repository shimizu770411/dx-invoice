# 請求書の画面合計とPDF合計の食い違い（調査結果・2026-09-15 / 対応完了・2026-09-17）

請求書の備考欄「葬儀代金」が画面とPDFで違う、という報告（画面 89,700円 / PDF 111,700円）の調査結果。
本番データをローカルに復元し、請求書23件について画面側・PDF側の合計計算をそれぞれ再現して突き合わせた。

**調査時の結論: 合計計算が画面とPDFで二重に実装されており、条件が5か所ずれている。**

**対応状況（2026-09-17時点）: 5項目すべて対応済み。**
金額の判定は `lib/documentTotals.ts` に一本化され、画面・保存処理・請求書PDF・領収書PDFが
すべて同じ処理を通る。PDF側の独自実装は残っていない。

| 項目 | 内容 | 状態 |
| --- | --- | --- |
| 1 | プラン別商品設定が請求書の編集画面に未適用 | 対応済み（+ 種類の引き直しも追加対応） |
| 2 | 解約手数料を消費税の対象に含めるか | 対応済み |
| 3 | 一般区分で会費入金を控除するか | 対応済み（運用判断あり） |
| 4 | 一般区分で満期サービス・施行割増券を減算するか | 対応済み（運用判断あり） |
| 5 | 複数行構成商品の会員単価 | 対応済み |

---

## 0. 前提: どこで何を計算しているか

### 調査時点

| 対象 | 計算している場所 |
| --- | --- |
| 請求書の編集画面の合計 | `lib/documentTotals.ts` の `calculateDocumentFormTotals` / `calcDocumentItemAmount` |
| 保存される明細の `amount` | 同上（`app/(protected)/invoices/hooks/useInvoiceForm.ts`） |
| 請求書PDFの合計・備考欄の葬儀代金 | `app/(protected)/pdf/components/PdfInvoiceLayout.tsx` の独自実装 |

PDF側は `calcDocumentItemAmount` を使っておらず、同じ判定を独立して書き直していた。

### 対応後

すべて `lib/documentTotals.ts` に集約済み。

| 関数 | 役割 |
| --- | --- |
| `computeNoChargeFor` / `isNoChargeFor` / `noChargeReasonFor` | 0円扱いの判定と、帳票に印字する区分 |
| `calcDocumentItemAmount` | 明細1行の金額 |
| `calcFreeItemsSubtotal` | フリー行の小計（解約手数料の除外・会員特典の適用可否を含む） |
| `calcGrandTotal` | 会費入金を差し引いた差引合計 |

`PdfInvoiceLayout` は会員価格列と一般価格列の両方を印字するため、同じ関数を会員・一般それぞれで呼ぶ。
この2ファイルから商品マスタの属性（`isSetChild` / `isDefaultSet` / `setableScope` 等）を
直接参照するコードは、型定義を除いて消えている。**判定式を再びここに書かないこと。**

さらに、発行済み書類の金額が後からの設定変更で動かないよう、明細に
`noChargeScope` / `noChargeReason`（0円扱いだった範囲と理由）を保存する仕組みを追加した。
表示・PDF・合計はこの控えを優先し、控えが無い書類（この列より前に作られたもの）だけ
現在の設定から判定し直す。

## 1. プラン別商品設定が請求書の編集画面に適用されていない【対応済み】

### 症状

請求書 `202609004`（プラン: 家族葬27万円コース、会員区分）

| 明細 | 画面 | PDF | 差 |
| --- | ---: | ---: | ---: |
| 霊柩車（基本料金・`product_row_id=53`, FIXED） | 0円 | 36,000円 | +36,000 |
| ドライアイス（`product_variant_id=29`） | 13,000円 | 0円 | -13,000 |
| **差引合計** | **86,400円** | **111,700円** | **+25,300** |

同じ原因で `202609005` `202609006` も 8,800円ずれている（いずれもプラン2）。

### 原因

PDF側は `getProductPlanSettings` + `applyPlanOverrides` で商品マスタにプラン別設定を反映してから
描画していたのに対し、請求書の編集画面は `getProducts()` の結果をそのまま使っており、
**プラン別設定を一切反映していなかった**。

`applyPlanOverrides`（`lib/plans.ts`）は合計計算の入力になる3つの値を書き換える:

- `productItem.setableScope`（プラン側の上書き値があれば優先）
- `productItem.isSetChild`（`overrideDefaultVariantId` 指定時に `true` へ昇格）
- `productVariant.isDefaultSet`（`overrideDefaultVariantId` の種類だけ `true`、他は `false`）

実データでの内訳（プラン2 = 家族葬27万円コース）:

| 商品 | 商品マスタ | プラン2の設定 | 結果 |
| --- | --- | --- | --- |
| 霊柩車 | `isSetChild=true`, `setableScope=MEMBER_ONLY` | `setable_scope=NONE` | マスタのままだと会員はセット0円。プラン適用後は課金対象 |
| ドライアイス | `isSetChild=false` | `override_default_variant_id=29`, `setable_scope=MEMBER_ONLY` | マスタのままだと課金。プラン適用後はセット0円 |

### 対応内容

`useInvoiceForm.ts` の `loadData` で、その請求書の `planId`（未設定なら `BASE_PLAN_ID`）の
プラン別設定を取得し、`applyPlanOverrides` を掛けてから明細をマージするようにした。

**調査時に挙がっていなかった問題がもう1つあった。** 商品一覧にプラン設定を適用するだけでは足りず、
**保存済み明細が参照している `productVariant` も引き直す必要がある**。セット0円の判定は
種類側の `isDefaultSet` を見るが、保存済み明細に付いてくる種類は商品マスタ由来でプランの
上書きが反映されていないため、条件を満たさず満額のままになる。
プラン適用後の種類一覧から同じIDの種類を探して差し替えるようにした。
探すのは保存済みの種類IDなので、担当者が選んだ種類そのものは変わらない。

この引き直しは**見積の編集画面にも同じ問題があった**ため、そちらにも入れてある
（`useEstimateForm.ts` の `buildEstimateItemsForProduct`。保存済み明細を引き継ぐ4経路すべて）。

また、商品マスタから消えた商品を補う処理はプラン適用の**後**に実行する。
逆順だと、補った商品がプランの非表示設定に引っかかって明細ごと消え、保存時に失われる。

補足: **請求書にプラン切替UIは無い**（見積で確定したプランを引き継ぐだけ）。
そのため読み込み時に適用するだけでよく、見積側の `handlePlanChange` 相当は不要。

### 波及

保存される明細の `amount` は画面側の計算なので、**DBに入っている金額も誤っていた**。
`invoices.subtotal / tax / total / grand_total` と領収書PDFの合計欄にも波及する。
既存データの遡及修復は試験運用中のため行わない（書類を開き直して保存すれば正しい値に入れ替わる）。

## 2. 解約手数料を消費税の対象に含めるかどうか【対応済み】

- 画面: フリー項目の小計に入れて課税していた
- PDF: 小計から除外し、合計欄に「解約手数料」「値引」の2行として表示（消費税対象外）

**PDF側の扱いが正で、画面が誤り**（ユーザー確認済み）。解約手数料は消費税の対象外で、
同額の値引と相殺されるため請求額に影響しない。

`isCancellationFeeRow` による除外を共通処理に入れ、画面・保存側の小計から外した。
判定はこの関数に集約してあり、請求書PDF・領収書PDFも同じ関数を使う。

影響額（修正前）: `202608004` 28,160円 / `202608008` 35,640円 / `202608009` 28,820円

## 3. 一般区分で会費入金を控除するかどうか【対応済み】

- 画面: 会員/一般に関係なく `total - membershipPaidAmount`
- PDF: 会員価格列だけ控除し、一般価格列は控除しない

### 運用判断（ユーザー回答・2026-09-17）

> 会費入金した時点で会員になり、一般価格で請求しない。

つまり「会費入金がある顧客を一般区分で請求する」という組み合わせは**運用上ありえない**。
一般区分で会費入金が登録されている書類は、**会員区分の設定漏れ**として扱う。

PDFの一般価格列は全書類に印字される「互助会に入っていなければこの金額」という比較表示なので、
会員特典である会費入金を効かせないのが正しい。**PDF側の扱いが正。**

### 対応内容

- 計算: `calcGrandTotal(total, membershipPaidAmount, isMember)` に集約し、会員区分の書類でのみ控除する。
  画面・保存処理・請求書PDF・領収書PDFがすべてこれを通る。
  保存処理の合計計算（`calculateDocumentTotals`）には会員区分を**必須引数**にしたので、
  渡し忘れると型チェックで止まる。
- 入力: 会費入金がある顧客を一般区分で保存しようとすると、見積・請求書の両方で確認メッセージを出す
  （`buildMembershipMismatchWarning`）。区分の設定漏れに気づけるようにするのが本筋、というユーザー判断による。

影響額: `202606001` 270,000円 / `202607001` 570,000円 / `202607002` 570,000円
（いずれも一般区分なのに会費入金がある＝区分の設定漏れと思われる書類）

## 4. 一般区分で満期サービス・施行割増券のフリー項目を減算するか【対応済み】

- 画面: 全フリー項目を小計に入れる（マイナス金額の満期サービスも減算される）
- PDF: 一般価格列からは `満期サービス` `施行割増券` を除外

### 運用判断

満期サービスは互助会の積立満期に対する特典、施行割増券は会員向けの割引券。
いずれも**互助会員だけに効く割引**なので、一般の書類では差し引かない。**PDF側の扱いが正。**

同じ理屈で、**明細行の満期サービス扱いも会員限定に統一した**（従来は画面・保存側が
会員区分を見ずに0円にしており、PDFだけ会員限定だった）。

### 対応内容

- 計算: `calcFreeItemsSubtotal(freeItems, isMember)` に集約。会員特典の判定は
  `isMemberBenefitFreeRow` にまとめてある。
- 入力: 一般区分の書類では、満期サービス・施行割増券のフリー行にチェックボックスを出さず、
  区分欄に「会員のみ」と表示する。明細行の満期サービスも一般区分ではチェックを出さない。
  既存データの金額は保持したまま、計算に効かないだけにしてある。

影響額: 満期サービス 48,600円 のとき 53,460円（税込）。`202606001` `202607001` で発生。

## 5. 複数行構成商品の会員単価【対応済み】

- 画面: 複数行構成商品は会員/一般に関係なく常に `unitPriceGeneral`
- PDF: 会員価格列では `unitPriceMember`

調査時点では `expandMultiRowToItems` と `handleVariantChange` の複数行分岐が両方に同じ
`unitPrice` を入れているため、本番データでも `unit_price_general <> unit_price_member` の
複数行明細は0件で、金額差にはなっていなかった。

PDFを `calcDocumentItemAmount` に寄せたことで、**常に一般単価**（画面側の挙動）に統一された。
将来 `product_row_variants` に会員価格を持たせても静かに食い違うことはない。

## 検証方法

本番データをローカルへ復元（`.claude/skills/restore-prod-db-to-local`）したうえで、
請求書ごとに「画面側の計算」と「PDF側の計算」を別々に再現し、差分を突き合わせた。

突き合わせに使った条件（調査時点 → 対応後）:

| 判定 | 画面側（調査時点） | PDF側（調査時点） | 対応後 |
| --- | --- | --- | --- |
| プラン別設定 | 反映しない | 反映する | 反映する（明細の種類も引き直す） |
| セット0円 | `isSetChild && isDefaultSet && scopeApplies(setableScope)` | 同じ（入力値はプラン反映後） | 共通処理に集約。保存時の控えを優先 |
| 満期サービス扱い（明細行） | 会員・一般とも0円 | 会員のみ0円 | 会員のみ0円 |
| 解約手数料 | 小計に含める | 小計から除外 | 小計から除外 |
| 満期サービス・施行割増券（フリー行） | 常に小計に含める | 会員列のみ含める | 会員の書類のみ含める |
| 会費入金 | 常に控除 | 会員列のみ控除 | 会員の書類のみ控除 |
| 複数行構成商品の単価 | 常に一般単価 | 列に応じた単価 | 常に一般単価 |
| 任意セット指定（`adhocSetScope`） | 子商品にも適用 | 子商品にも適用 | 子商品には適用しない（画面の明細行の実装に揃えた） |

### 回帰テスト

`lib/__tests__/documentTotals.test.ts` と `lib/__tests__/documentUtils.test.ts` に追加済み。

- 0円扱いの判定（セット / サービス / 満期サービス / 任意セット / 複数行構成商品）と、会員・一般の組み合わせ
- **算出した金額が0円であることと、0円扱いの判定が必ず一致すること**（両者がズレると「0円と表示しているのに合計には金額が入っている」書類ができる）
- 保存される合計と画面の合計が一致すること
- 保存時の控えがあれば、商品マスタ側が変わっても金額が動かないこと
- 控えの「課金と記録済み（NONE）」と「未記録（null）」を取り違えないこと
- 会員特典（会費入金・満期サービス・施行割増券）が会員の書類でのみ適用されること

`lib/__tests__/documentFieldCoverage.test.ts` は、明細の列が保存経路すべてに通っているかを検査する。
明細に列を足すと必ずここで落ちるので、`formEditable` / `serverManaged` への追記を忘れないこと。

なお `vitest` の対象は `*.test.ts` のみで `.tsx` を含まないため、
`DocumentItemTable` と `PdfInvoiceLayout` にはテストを書けない。
**判定ロジックを `lib/` に置き続けることが、この機能を守る唯一の手段**になる。
