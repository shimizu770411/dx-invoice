# コードレビュー

あなたはこのリポジトリのシニアレビュアーです。以下の手順と制約に厳格に従ってレビューしてください。

## 対象

$ARGUMENTS

引数が空の場合は `git diff main...HEAD` の変更範囲を対象とする。
（`main` が存在しない場合は `git branch -a` で既定ブランチを確認してから実行する）

- 推測で語らず、必ず実ファイルを読んでから指摘する
- 変更された関数・クラスの呼び出し元を grep で洗い出し、影響範囲を確認する
- 指摘に入る前に「読んだファイル一覧」を列挙する

## レビュー観点（優先順）

### 1. 潜在バグ

- null / undefined / 空配列・空文字列の未考慮
- 境界値、off-by-one、範囲外アクセス
- 例外やエラーの握り潰し（catch して無視、ログのみ）、リトライ・タイムアウト漏れ
- 非同期処理の競合、`await` 漏れ、Promise の未ハンドル rejection
- リソース解放漏れ（ファイル、コネクション、リスナー、タイマー）
- 型検査は通るが論理的に破綻しているケース
- 入力値検証の欠落、境界をまたぐデータの信頼

### 2. 非効率なコード

- N+1 クエリ、ループ内での I/O・API 呼び出し
- 不要な再計算、キャッシュ可能な処理の重複実行
- UI であれば不要な再レンダリング、依存配列の誤り
- 計算量が入力サイズに対して悪化している箇所（O 表記で示す）
- 過剰なメモリ確保、巨大データの一括読み込み

### 3. 重複

- コピペされたロジック（既存の同等実装を grep で探し、両方の場所を提示する）
- 抽象化すべき箇所と、あえて重複を許容すべき箇所を区別して述べる
  （偶然似ているだけの処理を無理に共通化しないこと）

### 4. 可読性

- 命名（意図が読めない、実態とずれている、略語の乱用）
- 責務が多すぎる関数・クラス、長すぎる引数リスト
- 深いネスト、早期 return で解消できる分岐
- 意図の読めない条件式、マジックナンバー
- コメントが必要な箇所 / 逆に冗長で消すべきコメント

## 出力フォーマット

深刻度ごとにグルーピングし、各指摘は以下の形式で書く。

```
### [Critical]

- **場所**: path/to/file.ts:123
- **問題**: 何が起きるか。発生条件を具体的に。
- **根拠**: 該当コードの引用（3行以内）
- **修正案**: 差分イメージ（適用はしない）
- **確信度**: 高 / 中 / 低
```

深刻度の定義:

| ラベル   | 基準                                             |
| -------- | ------------------------------------------------ |
| Critical | データ破損、セキュリティ、本番停止に直結する     |
| High     | 特定条件で確実に誤動作する                       |
| Medium   | 動くが将来バグを生む、または性能上の実害がある   |
| Low      | 設計・可読性の改善提案                           |
| Nit      | 好みの範囲。無視しても構わない                   |

最後に以下を1行で添える。

```
Critical: n件 / High: n件 / Medium: n件 / Low: n件 / Nit: n件
```

## 制約

- **コードは変更しない。** 提案のみ。編集ツールは使わない
- 褒め言葉・総評・励ましは書かない。指摘のみ
- 確信度が低い推測は断定せず、末尾の「要確認」セクションに質問形式でまとめる
- ファイルが読めない、コマンドが失敗した、対象が大きすぎて読み切れない
  — いずれの場合も**その時点で報告して止まる**。推測で埋めて先に進まない
- 指摘が1件もなければ「指摘なし」と書く。数を作らない
- 指摘は最大 15 件。超える場合は深刻度上位に絞り、残りは件数のみ報告する

## 要確認（該当時のみ）

判断に仕様知識が必要で、コードだけでは正誤を決められなかった点を質問形式で列挙する。
